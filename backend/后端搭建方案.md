## 二、Phase 1：MVP 最小后端（2-3 天）

### 目标
前端改一行 `VITE_USE_MOCK=false` 即可切换真实后端，所有页面正常运作。

### 技术选型

| 层面 | 选型 | 原因 |
|------|------|------|
| Web 框架 | FastAPI | 需求指定，异步高性能，自动生成 Swagger 文档 |
| 数据库 | SQLite（aiosqlite） | 零配置，单文件，开发阶段无需安装数据库服务 |
| ORM | SQLAlchemy 2.0 异步 | FastAPI 生态标准，支持异步查询 |
| 认证 | JWT（python-jose） | 需求指定 |
| 密码加密 | bcrypt（passlib） | 需求指定 |
| 部署 | `uvicorn main:app --reload` | 单进程热重载 |

### 技术选型详细依据

**FastAPI 选择理由**：
- 原生支持 `async/await`，适合 I/O 密集型场景（数据库查询、外部 API 调用）
- 自动生成 OpenAPI 文档（Swagger UI），前后端联调效率高
- 依赖注入系统天然适合数据库会话管理和认证中间件
- Pydantic 集成提供请求参数自动校验，减少手写校验代码

**SQLite + aiosqlite 选择理由**：
- MVP 阶段单用户/少用户，无需数据库服务安装和配置
- 单文件数据库便于版本控制和数据迁移
- aiosqlite 提供异步接口，与 FastAPI 异步模型一致
- 后续迁移 PostgreSQL 仅需改连接字符串，SQLAlchemy ORM 层无感知

**SQLAlchemy 2.0 异步选择理由**：
- 2.0 版本原生支持 `async session`，与 FastAPI 配合无阻塞
- 声明式映射（Declarative Base）代码简洁，表定义可读性强
- 支持 `select().where()` 链式查询，类型安全
- 迁移工具 Alembic 生态成熟，Phase 2 数据库升级有保障

**JWT 认证选择理由**：
- 无状态认证，服务端不存储 Session，适合后续多实例部署
- Token 携带用户角色和村庄 ID，便于 Phase 2 实现 RBAC 行级隔离
- 前端已实现 `Authorization: Bearer ${token}` 拦截器，协议对齐零成本

## 三、系统架构设计

### 3.1 请求处理流程

```
浏览器/Vue 前端
    │
    ├── HTTP 请求 ──→ Vite Dev Server (5173) ──→ CORS ──→ FastAPI (8000)
    │                                                        │
    │                                                   中间件层
    │                                                   ├─ CORSMiddleware（跨域）
    │                                                   ├─ ExceptionHandler（统一错误格式）
    │                                                   └─ get_current_user（JWT 鉴权）
    │                                                        │
    │                                                   路由层（Routers）
    │                                                   ├─ auth.py      → 登录签发 Token
    │                                                   ├─ alerts.py    → 告警 CRUD
    │                                                   ├─ elders.py    → 老人档案
    │                                                   ├─ tasks.py     → 走访任务
    │                                                   └─ devices.py   → 设备 + 用量
    │                                                        │
    │                                                   数据层（SQLAlchemy）
    │                                                   ├─ async_session → 独立会话/请求
    │                                                   └─ SQLite (data/edgefall.db)
    │
    └── WebSocket ──→ ws://localhost:8000/ws/v1/admin/alerts
                         │
                     MVP 占位端点（PING/PONG 心跳）
                     Phase 2: ws_manager.py 广播告警
```

### 3.2 统一响应格式

所有接口遵循 `{ code: 200, data: ... }` 格式，与前端 `request.js` 拦截器对齐：

```python
# 成功响应
{"code": 200, "data": {...}}

# 错误响应（由 ExceptionHandler 统一处理）
{"code": 401, "data": {"detail": "Token 已过期，请重新登录"}}
{"code": 404, "data": {"detail": "老人不存在"}}
{"code": 422, "data": {"detail": "参数校验失败"}}
```

前端拦截器行为：
- `code === 200` → 返回 `data` 给组件
- `code !== 200` → 弹出 `data.detail` 错误提示
- HTTP 401 → 清除 Token + 跳转登录页

### 3.3 认证流程

```
1. 用户提交 username + password → POST /auth/login
2. 后端 bcrypt 验证 → 签发 JWT（含 user_id, role, village_id）
3. 前端存储 Token 到 localStorage
4. 后续请求自动附加 Authorization: Bearer <token>
5. get_current_user 依赖注入解析 Token → 返回 Account 对象
6. 业务路由通过 Depends(get_current_user) 强制鉴权
```

JWT Token 结构：
```json
{
  "sub": "1",                    // 用户 ID
  "role": "village_grid",        // 角色
  "village_id": 1,               // 村庄 ID
  "exp": 1718668800              // 过期时间（24h）
}
```

### 3.4 数据交互关键映射

以下映射确保后端返回数据与前端组件赋值语句完全一致：

| 后端存储 | 后端返回转换 | 前端读取 |
|---------|------------|---------|
| `alerts.title/location/ai_diagnosis` 扁平字段 | 组装为 `payload: { title, location, ai_diagnosis }` | `alert.payload?.location` |
| `elders.risk_tags` JSON 字符串 | `json.loads()` 反序列化为数组 | `e.risk_tags` 直接遍历 |
| `api_usage` 按行存储（ezviz/qwen） | 组装为 `{ ezviz_api: {...}, llm_qwen: {...} }` | `apiUsage.llm_qwen.tokens_today` |
| `devices.is_online` INTEGER | `bool(d.is_online)` 转布尔 | `d.is_online` 判断 |
| `elders` 无 `recent_activities` 列 | MVP 返回静态活动数据 | `elder.recent_activities` 遍历 |
| `elders` 无 `ai_report` 列 | `/ai-report` 端点返回静态文本 | `aiReport.ai_summary` |

## 四、安全策略

### 4.1 认证与授权

| 安全项 | MVP 实现 | Phase 2 增强 |
|--------|---------|-------------|
| 密码存储 | bcrypt 哈希（自动加盐） | 同左 |
| Token 签发 | JWT HS256，24h 过期 | 缩短至 2h + Refresh Token |
| Token 验证 | `get_current_user` 依赖注入 | 同左 + Redis 黑名单 |
| 角色校验 | JWT payload 含 role，路由层暂未强制校验 | RBAC 装饰器，按角色限制接口访问 |
| 数据隔离 | 暂无（所有用户可见全量数据） | 按 `village_id` 过滤，网格员只看本村 |
| WebSocket 鉴权 | MVP 占位端点不校验 Token | Phase 2 连接时验证 Token 有效性 |

### 4.2 输入安全

| 安全项 | 实现方式 |
|--------|---------|
| SQL 注入 | SQLAlchemy ORM 参数化查询，不拼接 SQL |
| XSS | FastAPI 自动 JSON 序列化，不渲染 HTML |
| 请求体校验 | Pydantic `Field` 约束（min_length、max_length、pattern 正则） |
| 请求大小限制 | uvicorn 默认限制，MVP 足够 |
| CORS 白名单 | 仅允许 `localhost:5173`（Vite 开发服务器） |

### 4.3 敏感信息保护

| 安全项 | 实现方式 |
|--------|---------|
| JWT 密钥 | `.env` 文件存储，不提交 Git（`.gitignore` 排除） |
| 数据库文件 | `data/` 目录不提交 Git |
| 密码明文 | 仅种子数据默认密码 `123456` 在日志中输出，生产环境必须修改 |
| Token 日志 | WebSocket 占位端点仅打印 Token 前 20 字符 |

## 五、性能优化方案

### 5.1 MVP 阶段（当前）

| 优化项 | 实现方式 | 说明 |
|--------|---------|------|
| 异步 I/O | FastAPI + aiosqlite + async SQLAlchemy | 请求处理不阻塞事件循环 |
| 数据库连接复用 | `async_sessionmaker` 连接池 | 默认池大小 5，MVP 足够 |
| 按需查询 | 告警列表 `status` 过滤 + 设备列表 `type` 过滤 | 避免全表扫描 |
| 索引优化 | `accounts.username` 唯一索引 | 登录查询 O(1) |
| 响应精简 | 仅返回前端需要的字段 | 手动构造 dict，不暴露 ORM 内部属性 |

### 5.2 Phase 2 性能增强

| 优化项 | 实现方式 | 说明 |
|--------|---------|------|
| 数据库迁移 | SQLite → PostgreSQL | 支持并发写入，连接池更高效 |
| 缓存层 | Redis 缓存设备状态、API 用量 | 减少数据库查询 |
| 索引增强 | `alerts.status`、`elders.name`、`devices.type` 加索引 | 列表查询加速 |
| 分页优化 | 游标分页替代 OFFSET | 大数据量下 OFFSET 性能差 |
| WebSocket 推送 | 替代前端轮询 | 告警实时性从秒级降到毫秒级 |

### 5.3 Phase 3 性能增强

| 优化项 | 实现方式 | 说明 |
|--------|---------|------|
| 时序数据库 | TDengine 存储手环/门磁数据 | 时序查询性能比关系型数据库高 10x |
| 异步任务 | Celery 处理大模型调用、报告生成 | 不阻塞 API 请求 |
| 负载均衡 | Nginx 反向代理 + 多 uvicorn Worker | 支持并发请求 |
| 容器化 | Docker Compose 编排 | 一键部署，资源隔离 |

## 六、错误处理策略

### 6.1 统一异常处理

```python
# main.py 中注册全局异常处理器
@app.exception_handler(HTTPException)
async def http_exception_handler(request, exc):
    return JSONResponse(
        status_code=exc.status_code,
        content={"code": exc.status_code, "data": {"detail": exc.detail}}
    )

@app.exception_handler(Exception)
async def generic_exception_handler(request, exc):
    return JSONResponse(
        status_code=500,
        content={"code": 500, "data": {"detail": "服务器内部错误"}}
    )
```

### 6.2 错误码规范

| HTTP 状态码 | code | 场景 |
|:--:|:--:|------|
| 200 | 200 | 请求成功 |
| 400 | 400 | 参数校验失败、重复操作 |
| 401 | 401 | 未登录、Token 过期、Token 无效 |
| 404 | 404 | 资源不存在 |
| 422 | 422 | Pydantic 请求体校验失败 |
| 500 | 500 | 服务器内部错误 |

### 6.3 JWT 异常处理

```python
# get_current_user 中完整捕获 JWT 异常
try:
    payload = jwt.decode(token, settings.jwt_secret_key, algorithms=[settings.jwt_algorithm])
except jwt.ExpiredSignatureError:
    raise HTTPException(status_code=401, detail="Token 已过期，请重新登录")
except jwt.JWTError:
    raise HTTPException(status_code=401, detail="Token 无效，请重新登录")
```

## 十、需求分析中不可行或不合理的功能

### 技术上不可行

| 功能 | 原始描述 | 实际问题 |
|------|---------|---------|
| **UWB 厘米级室内定位** | 手环 DW1000 芯片 + 网关实现厘米级定位 | UWB 需要至少 3 个固定基站（Anchor）做三角定位。农村家庭每个房间部署基站成本高、非视距精度急剧下降到 1-3 米，达不到厘米级。 |
| **萤石摄像头"骨骼关键点 API"** | 联动萤石 C6CN 摄像头骨骼关键点 API 进行视觉二次核验 | 萤石开放平台不提供骨骼关键点 API。骨骼关键点识别（OpenPose/MediaPipe）需要本地 GPU 推理，摄像头端不具备此能力。萤石只提供视频流和人形检测。 |
| **手环蓝牙同步手机通话状态** | 手环通过蓝牙获取老人手机通话状态 | 手机通话状态是操作系统级权限，需要手机上安装配套 App 才能获取（Android TelecomManager / iOS CallKit）。纯手环硬件无法直接读取。 |

### 效果存疑

| 功能 | 问题 |
|------|------|
| VAD 音频"语速/叹气频率/泛音"判断抑郁 | 非受控环境（电视声、多人说话）下语音分离极难。学术研究中叹气检测准确率仅 60-70%，"泛音"分析需要高质量近距离录音。结论置信度很低。 |
| 心率异常 + 通话时长 → 诈骗预警 | 心率飙升原因很多（激动、运动、身体不适），与诈骗无因果性。误报率会极高。诈骗识别应依赖通话内容 NLP 语义分析。 |
| 边缘网关联动全屋系统语音阻断 | 农村家庭基本不具备"全屋智能家居系统"，此功能无硬件环境支撑。 |

### 法律合规风险

| 功能 | 风险 |
|------|------|
| 大模型生成"伤情预判"和"急救指引" | 大模型不具备医疗诊断资质。错误急救建议可能导致人身损害，开发者承担法律责任。 |
| VAD 录音采集 | 需明确告知老人及家属并征得同意，否则涉及侵犯隐私权。 |

### 建议调整

| 原始设计 | 建议改为 |
|---------|---------|
| UWB 厘米级定位 | BLE RSSI + 门磁 + 红外 → 房间级定位（知道在哪个房间） |
| 骨骼关键点核验跌倒 | 萤石 AI 人形检测 + 移动侦测 → "画面中是否有人形在动" |
| 大模型生成急救指引 | 只生成风险等级 + "建议联系村医/拨打 120"，不给具体操作 |
| 诈骗实时阻断 | 高危词匹配 → 手环震动 + 通知子女，不做全屋广播 |
| VAD 情绪分析 | 改为"每日说话频率"作为社交活跃度参考指标 |

## 十一、已知限制与风险

### 11.1 MVP 阶段已知限制

| 限制 | 影响 | 缓解措施 |
|------|------|---------|
| SQLite 并发写锁 | 多用户同时写入会锁库 | MVP 单用户开发阶段无影响；Phase 2 迁移 PostgreSQL |
| 前端搜索逻辑冲突 | ElderRoster.vue 本地 computed 过滤 + 后端分页可能冲突 | MVP 数据量小（5 条），问题不明显；Phase 2 统一为服务端搜索 |
| WebSocket 不推送真实告警 | 前端无法实时收到告警 | 占位端点避免重连风暴；用户手动刷新页面获取新告警 |
| AI 报告为静态文本 | 所有老人看到相同报告 | Phase 2 接入大模型按需生成 |
| 无 RBAC 数据隔离 | 网格员可看到其他村数据 | MVP 仅演示用；Phase 2 按 village_id 过滤 |
| 种子数据路径硬编码 | `seed.py` 跨目录引用 `edgefall-web/src/mock/` | 仅开发阶段使用，部署时不需要 |

### 11.2 技术风险与应对

| 风险 | 概率 | 影响 | 应对方案 |
|------|:--:|:--:|---------|
| bcrypt 哈希性能差（CPU 密集） | 低 | 中 | MVP 用户量小无影响；生产环境可调低 rounds 或换 argon2 |
| JWT 密钥泄露 | 中 | 高 | `.env` 不提交 Git；生产环境使用强随机密钥 + 环境变量注入 |
| SQLite 数据库文件损坏 | 低 | 高 | 定期备份；Phase 2 迁移 PostgreSQL |
| 前后端数据格式不一致 | 中 | 高 | 步骤文档中每个接口已标注前端赋值语句，严格对齐 |
