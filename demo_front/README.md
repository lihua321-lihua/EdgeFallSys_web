### 一、 村委会端（业务后台）需求分析

**目标用户：** 村支书、驻村网格员、村医。 **核心诉求：** 快速知道谁出事了、谁需要去走访看看、老人的档案在哪。 **UI 基调：** 拒绝深色炫酷大屏。采用类似政务系统的浅色底板，大字号，以列表和弹窗为主，零学习门槛。

#### 1. 紧急工单台（核心首页）

这是村委会人员每天盯着的页面，只处理实打实的事情。

- **高亮待办列表：** 按紧急程度排序。
  - **红色（紧急）：** 手环或网关发来的跌倒报警。必须包含：发生时间、老人姓名、当前位置（如：王大爷，卫生间）。
  - **橙色（高危）：** 拦截到的诈骗电话预警、陌生人入户预警。
- **极简处理流程：** 每条告警右侧只有一个【接单处理】按钮。点击后弹出处理记录框，勾选“已上门/已联系家属/误报”，点击提交后工单消失，形成闭环。

#### 2. 辖区老人名册（电子档案室）

替代纸质档案，结合多模态数据生成动态名册。

- **基础信息表：** 姓名、年龄、住址、绑定的手环/网关编号、家属紧急联系电话。
- **健康与心理体检表（AI生成）：** * 不展示复杂的“语速、泛音、基频”等底层数据（村干部看不懂）。
  - **直接展示大模型结论：** 每月自动更新。例如：“经系统分析，本月张奶奶情绪低落指数较高，步态平稳度下降，存在一定的孤寡抑郁及跌倒风险”。

#### 3. 关怀走访任务清单（变被动为主动）

系统通过分析数据，主动给村干部派活。

- **系统自动派发：** 如果系统发现某位老人“连续 3 天大门门磁未触发（未出门）”或“手环 UWB 轨迹极度单一”，自动生成一条【建议走访】任务。
- **任务流转：** 网格员上门走访后，在系统内简单填写走访反馈（如：老人感冒卧床，已通知村医拿药）。

### 二、 管理员端（运维后台）需求分析

**目标用户：** 乡镇IT维护人员、系统实施人员（也就是你们团队自己）。 **核心诉求：** 确保硬件设备全都在线，确保系统 API 没欠费，管理各村的账号。 **UI 基调：** 标准的后台管理系统（Admin Dashboard），注重信息密度和批量操作。

#### 1. 设备资产与状态生命周期

这是硬件运维的命脉。

- **设备台账：** 统一管理手环（MAC地址）、边缘网关（IP/SN）、萤石摄像头（SN码）的入库与分配。
- **在线状态监控表：**
  - 实时显示手环电量（%）、4G 模块信号强度、蓝牙连接状态。
  - **离线告警：** 若边缘网关离线超过 2小时，或手环电量低于 10%，系统生成【设备运维单】，提醒管理员去更换电池或重启网关。
- **快速换绑：** 设备损坏时，支持一键解绑旧设备、录入新设备 MAC，且不丢失老人的历史数据。

#### 2. 组织架构与账号管理

- **村级节点分配：** 创建并管理不同村庄/社区的节点。
- **角色权限（RBAC）：** 配置“村级网格员”（只能看本村工单）、“村医”（只能看健康档案）、“超级管理员”（查看全盘数据）的权限路由。

#### 3. 开放平台 API 监控台

防止比赛演示或实际落地时，调用的第三方服务突然断供。

- **萤石开放平台用量：** 实时监控骨骼关键点、语音识别等 API 的每日调用次数是否逼近免费额度上限。
- **大模型服务监控：** 监控 Qwen 或其他大模型的 Token 消耗量及接口响应延迟（判断网络或服务是否健康）。

### 三、 非功能性（技术保障）需求

为了支撑上述务实的功能，采用 Vue 3 和 FastAPI 进行前后端分离开发时，需要注意以下硬性技术需求：

1. **强实时性推送：** 村委会端的“紧急工单台”必须使用 **WebSocket** 建立长连接。老人在家里跌倒，村委会的网页必须在 1 秒内弹出红色报警框并拉起报警音，绝不能用定时刷新（轮询）来凑合。
2. **数据极简加载：** 为了适配基层可能存在的办公老旧电脑或较差的网络环境，前端页面尽量少用重型渲染库，做到列表秒开。
3. **大模型异步处理：** 收到录音或跌倒数据时，FastAPI 后端请求大模型生成报告的过程必须是异步的（Async/Await 或采用 Celery 任务队列），绝不能阻塞硬件告警的快速流转。
